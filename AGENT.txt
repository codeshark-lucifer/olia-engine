# Vulkan Rendering Investigation Task

## Objective

Perform a deep root-cause investigation into a Vulkan rendering bug. Do **not** provide generic Vulkan advice or a list of common mistakes. Instead, trace the rendering pipeline from CPU memory to the final framebuffer and determine the exact cause.

---

## Problem

A cube renders correctly.

- Geometry is correct.
- Normals appear correct.
- Material color is white.
- Light color is white.
- Lighting direction is correct.

However, the shadowed (dark) side of the cube appears **purple/blue** instead of gray.

The lighting itself appears correct until it is multiplied by the material color.

Example:

```glsl
vec3 result = ambient + diffuse + specular;

outColor = vec4(result, 1.0);          // Correct grayscale

outColor = vec4(result, 1.0) * material.color;
// Dark regions become purple
```

Yet:

```glsl
outColor = material.color;
```

renders a completely white cube.

Also:

```glsl
outColor = vec4(lights[0].color.rgb, 1.0);
```

renders completely white.

This suggests both operands appear correct individually, but not when combined.

---

## Already Verified

- Cube mesh is correct.
- Vertex normals are correct.
- `fragWorldPos` is correct.
- Normal matrix uses inverse transpose.
- Material color outputs pure white.
- Light color outputs pure white.
- Outputting `vec4(result, 1.0)` produces grayscale lighting.
- Outputting `vec4(0,0,0,1)` produces pure black.
- Swapchain appears correct.
- Render pass appears correct.
- Descriptor bindings appear correct.
- CPU and GLSL material layouts appear to match.
- Push constants appear correct.
